# Adler app API contract (`/api/app/*`)

The native app is a presentation adapter for the existing coaching system. Every screen reads a
typed view that the server derives from `shared/*.ts` — the same functions the web renders — and
every deterministic edit goes through the shared command catalog. The client renders; it does not
derive. No label, delta, standing, status or assumption sentence in this document should be
recomputed on the device.

- Authoritative TypeScript types: **`shared/app-views.ts`**.
- Routes: **`server/app-api.ts`**, mounted from `server/api.ts`.
- Real example payloads: **`docs/ios-api-examples/*.json`**, regenerated by
  `npx tsx scripts/app-api-examples.ts` from a fictional account (`casey-example`). Every file is
  `{ "request": string, "status": number, "response": … }`.

## 1. Transport, auth and host rules

| Item | Value |
| --- | --- |
| Base path | `/api/app/` |
| Content type | `application/json`; every response sends `Cache-Control: private, no-store` |
| Auth | the existing HttpOnly session cookie `adler_session` (30 days), set by `POST /api/auth/register` and `/api/auth/login` |
| Sign out | `POST /api/auth/logout` |
| CSRF | a request is refused with 403 when `Origin` is a foreign origin or `Sec-Fetch-Site: cross-site`. `URLSession` sends neither, so native requests pass |
| Host | without `PUBLIC_URL` the server accepts `localhost`, `127.0.0.1`, `[::1]` and — only when `NODE_ENV !== "production"` — RFC1918 private IPv4 hosts (`10/8`, `172.16/12`, `192.168/16`). Any other `Host` is 403 `{"error":"Unrecognized host."}` |
| Rate limit | 600 app requests per user per minute (429 `{"error":"Too many requests. Please try again later."}`) |
| Live updates | `GET /api/events` (SSE) emits `data: {"revision":N}`. Refetch the visible views when `N` changes |

`URLSession` stores the cookie automatically with a shared `HTTPCookieStorage`. Do not add an
`Origin` header.

## 2. Revision, idempotency and errors

Every view carries `revision` (the workspace version) and `today` (the account-local date,
`YYYY-MM-DD`, computed in the account's IANA `timeZone`).

- Writes send the `revision` the client last saw. A mismatch returns **409** with the current
  revision: `{"error":"This workspace changed in another channel. Review the latest records and retry.","revision":4}`. Refetch, then retry with the new revision.
- Writes send a `requestId` (8–100 characters; use a UUID). Replaying the identical
  `{changes, revision, requestId}` returns the first result and changes nothing. Reusing a
  `requestId` with different content is **400** `{"error":"A request ID cannot be reused for different changes."}`.
- Errors are always `{ "error": string }` with a 4xx status: 400 validation or a refused edit, 401
  `Sign in to your workspace.`, 403 host/CSRF, 404 unknown record or route, 409 stale revision, 429
  rate limit. The message is user-facing prose; show it.

### Nullability convention

Optional data is `null`, never an omitted key — with two exceptions, both documented at their
endpoint: `goal` in a write response, and `undefined` query parameters. In Swift, a field typed
`T | null` is `T?`; a field typed `T` is non-optional. Arrays are always present, possibly empty.

## 4. Reads

All reads are `GET`, take no body, and return 200 or an error. `today` and `revision` are present on
every one.

### `GET /api/app/session` → `SessionView` · `session.json`

`{ revision, today, user {id, username}, preferences {timeZone, theme, reviewDay, automation}, status { coach {configured, provider, model}, calendars { google {configured, connected}, apple {connected} }, serverKeysAllowed }, counts {goals, activeGoals, drafts, conversations}, reviewDue, hasGoals }`

`status.coach.configured` is false when no provider key is usable; onboarding shows provider setup
only in that case. `serverKeysAllowed` says whether the account may select "use this server's key".

### `GET /api/app/today` → `TodayView` · `today.json`

Refreshes plan occurrences first (same as `GET /api/workspace`), so the payload can carry a new
`revision`.

### `GET /api/app/goals` → `GoalsView` · `goals.json`

`budget` is the weekly bar: `weekStart`, `weekEnd`, `totalMinutes`, `budgetMinutes`, `overMinutes`,
`scaleMinutes`, `goals[] {goalId, title, status, color, minutes, proposed}`, `sourceNote`,
`programReason`. `rows[]` is one `GoalRow` per goal:

- `goal` (`GoalRef` with `color` as an `hsl(H S% L%)` string), `kind`, `priority`, `area`, `tags`,
  `success`, `resultLabel`, `current`, `target`, `unit`, `observedAt`
- `activity[]` — complete week columns ending with the current week, `?weeks=` (default 12). Each
  cell: `date`, `state`, `done`, `partly`, `missed`, `unknown`, `planned`, `level` (0–4)
- `activitySummary {reported, done, completion, label}` — `label` is `N% completed` or `No check-ins yet`
- `series` — a 14-day `InputSeriesView`, or `null` when the goal has no repeating measured step
- `stepTitle`, `nextAction {id, title, date, phase}`, `completedActions`
- `milestone {id, title, dueDate}`, `implication`, `outlook`, `outlookNote`, `projectionStatus`

`groups[]` orders goals by status (`Active`, `Draft`, `Paused`, `Completed`, `Set aside`); empty
groups are omitted. `areas[]` and `tags[]` are the filter values in use.

`InputSeriesView`: `measure`, `start`, `end`, `points[] {date, amount, planned, retired, future, scheduled, off, actionIds}`, `reported`, `plannedTotal`, `unknown`. `amount: null` is unknown;
`off: true` is a planned day without work (a rest day, not a miss).

### `GET /api/app/coach` and `GET /api/app/coach/:conversationId` → `CoachView`

`coach.json`, `coach-conversation.json`. 404 for an unknown conversation id.

- `conversations[]` — `ConversationRef {id, title, goalId, goalTitle, createdAt, messageCount, lastMessageAt, lastMessage}`, most recent first
- `selectedConversationId` — `null` on the list route
- `messages[]` — only when a conversation is selected. `MessageView`: `id`, `conversationId`,
  `goalId`, `goalTitle`, `role`, `origin`, `channel`, `text`, `at`, `decisionId`,
  `links[] {goalId, goalTitle, tab}`, `references[] {text, recordId}`,
  `reactions[] {actor, type, at}`, `authorLabel` (`Adler` / `You` / `Connected update`), `saved`,
  `recommendations[]`, `decisionSummary`, `decisionChecks[]`, `decisionMethods[] {id, name, url}`
- `proposals[]` — pending proposals only, filtered to the conversation when one is selected.
  `ProposalView`: `id`, `summary`, `headline`, `consequences[]`, `booking`, `affected`, `goalId`,
  `goalTitle`, `conversationId`, `decisionId`, `status`, `channel`, `expires` (epoch ms), `expired`,
  `createdAt`, `changes[]`, `before[]`, `recommendations[]`, `researchClaims[]`, `researchSources[]`
- `quickPrompts[]` — `{id, label, prompt, goalId}`, at most six, the same opening text the web
  deep-links. Send `prompt` as the message body of `POST /api/coach`
- `model` — `{configured, provider, model}`
- `goals[]` — `GoalRef[]` for the conversation folder picker

`consequences[]` states what accepting does before it happens, for example
`Accepting creates this event in your connected google calendar, with a separate check-in event.`,
`Accepting saves a new plan version. Reported and booked work is preserved.`,
`Changing the measurement archives the results recorded under the previous one.`. It is empty when
the changes carry none of those effects.
`booking` is non-null only when the proposal creates an **external** event:
`{provider, calendarName, start, end, includesCheckIn}`; `calendarName` is the calendar identifier
saved on the proposal (Google returns an address, Apple a CalDAV URL).
`affected` counts `{actions, milestones, planVersions}` — actions counts `action` and `workBlock`
changes; `planVersions` counts the distinct goals receiving a new plan version.
`changes[].values` and `before[]` are opaque JSON strings/objects in the command catalog's shape;
decode them lazily for the Current → Suggested comparison, or call
`POST /api/proposals/:id/preview` for the execution preview.

`RecommendationView`: `action`, `observation`, `interpretation`, `expectedEffect`, `goalIds[]`,
`sourceIds[]`, `reasoning` (principle ids, `goalRoute`, `ruleExceptions[]`, `barrier`, `methodId`,
`researchSourceIds[]`, `mechanism`, `fit`, `prediction`, `reviewRule`, `limitation`),
`grounding[]`, `sources[]`. Render these saved records; never compose a new explanation.

### `GET /api/app/insights` → `InsightsView` · `insights.json`

Query `goal` filters to one goal. Three lists of `LearningRow`, plus `observations` and `memories`:

- `tryingNow` — pending revision, or state `suggested` / `agreed` / `paused`, or standing
  `reconsider`, or a reviewed record with a next review date
- `learned` — finished records that have at least one saved review
- `history` — finished records with no review (declined or closed without feedback)

`LearningRow`: `recordId`, `version`, `activeVersion`, `pendingVersion`, `state`, `standing`,
`statusLabel`, `standingLabel`, `timingLabel`, `goals[]`, `change`, `observation`, `hypothesis`,
`behaviorSignal`, `mechanismSignal`, `outcomeSignal`, `prediction`, `reviewRule`, `comparison`,
`design`, `alternatives[]`, `transfer`, `start`, `reviewAfter`, `nextReviewAfter`, `reports`,
`latestReview {id, at, summary, implication, nextQuestion, decision, standing, standingLabel, exposure, exposureLabel}`,
`controls {agree, decline, pause, resume, close}`, `actionVersion`, `attempts[]`, `sources[]`,
`prompt`.

`attempts[]` are dated action reports inside the test — `{date, outcome, actionId}`, oldest first,
last 30 — scoped to the test's saved `inputStepIds` when it names them. A reported attempt is not
evidence that the change worked.

`sources[]` are the current version's resolved evidence records — `{id, kind, label, text, deepLink}` —
excluding `measurement` sources, as the web does. When the record has been deleted, `label` is
`Source removed`, `deepLink` is `null` and `text` explains it.

`observations[]` are the attributable observations and preferences a coach decision recorded — the
rows `src/Insights.tsx` renders — shown **beside** the learning records, never merged into them. An
observation needs no hypothesis or test scaffolding. A decision that a learning record already
carries (through a version or a review) is omitted, so nothing appears twice. Newest first, filtered
by `goal` like the rest of the view.

`ObservationRow`: `id` (`<decisionId>-<index>`), `decisionId`, `proposalId`, `date`, `finding`,
`status` (`Reported` | `To test`), `kindLabel` (`Your observation` | `Hypothesis` | `Working insight`),
`headline`, `statusLabel` (`Reported by you` | `To test` | `Earlier hypothesis` | `Feedback received`),
`implication`, `implicationLabel` (`What to explore next` | `Proposed adjustment` | `In the saved plan` | `Previously considered adjustment`),
`changeStatus` (`No plan change` | `Proposed` | `Saved` | `Not applied` | `Needs a fresh review`),
`changes[]` (the linked proposal commands, empty when none), `goals[]`, `goalIds[]`, `goalTitle`
(`Across your goals` when several goals are affected), `sources[]` and `resultSources[]` (resolved
with `sourceView`, same shape as `LearningRow.sources`), `research[]`, and `learning` — `null` for a
plain observation, otherwise `{recordId, goalIds, hypothesis, experiment, insight, nextHypothesis, previousInsightId, transfer, result, reasoning, grounding}`.
`changeStatus` reflects the linked proposal's own status, whether or not this row names any of its
changes, exactly as the web does.

`memories[]`: `{id, text, date, corrected, corrections[] {id, reason, at}}`.

### `GET /api/app/insights/:recordId` → `LearningDetailView` · `insight-record.json`

`{ revision, today, row, versions[], reviews[], events[], invalidations[], pending }`. 404 when the
record is gone. `versions[]` carry the full original reasoning with resolved `grounding[]` and

Query `start=YYYY-MM-DD` — any date inside the wanted week; the server snaps to Monday. An invalid

`{ user, preferences, status, provider {selected, providers[]}, connections {configured, provider, number, publicUrl, link, jobs[], deliveries[]}, tokens[] {id, name, scope, expires}, publicUrl, program, programs[] {version, date, reason}, methods[] (the seven method records with `enabled`), goals[] }`

## 5. Writes

### `POST /api/app/changes` · `changes.json`, `changes-conflict.json`

```json
{ "changes": [ { "entity": "action", "operation": "update", "id": "…", "parentId": null,
                 "reason": "Reported from the app right after the session.",
                 "values": "{\"outcome\":\"Done\",\"actualMinutes\":20}" } ],
  "revision": 2, "requestId": "3f0c…", "goalId": "portfolio" }
```

- `changes` — 1 to 50 commands from the shared catalog (`server/commands.ts`). `values` is a **JSON
  string** of only the fields to set. `reason` is optional but shown beside the change.
- `goalId` — optional; when present and the goal exists, the response includes its refreshed detail.
- Response **200**: `{ revision, today: TodayView, goal?: GoalDetailView }`. `goal` is **omitted**
  when no `goalId` was sent or the goal no longer exists.
- Response **409**: `{ error, revision }` — refetch and retry.
- Response **400**: any validation, capacity or ownership refusal, with the server's message.

The app uses this for: reporting an action outcome (`action` update with
`outcome` / `amount` / `actualMinutes` / `note` — omit an unknown amount, never send `0`), marking a
milestone `done`, adding a `result`, goal status changes (`Paused`, `Completed`, `Set aside`,
`Active`), preference and program edits, memory edits, local work blocks, conversation folders and
deleting a goal.

**Scientific records stay with the shared coach.** An app edit that introduces a plan `basis`,
`adaptive.reasoning` or `adaptive.experiment` not already saved is refused with
`New coaching explanations must use the shared coach, where their research and learning are reviewed. Manual edits can save your chosen work without adding a scientific claim.`
Learning records, evidence corrections and decisions are never writable here; use `POST /api/coach`,
the proposal routes or `POST /api/learning`.

### `POST /api/app/actions/:id/start` · body `{ "goalId"?: string }`

Runs `beginAction`: marks the action started now and dates it today. 404 for an unknown action; 400
`This action already started.`; 400 `This action can’t start yet. Its goal must be active, the action unreported, and any earlier work finished.`
Response shape is the same as `/api/app/changes`.

### `POST /api/app/goals/:id/start` · `goal-start.json`, `goal-start-blocked.json`

Activates a draft plan. 404 for an unknown goal; 400 `Only a draft plan can be started.`; 400
`Choose a first action before starting this goal’s plan.`; 400 (the review guard)
`This plan relies on corrected evidence. Review the update in Check-in before starting, or edit the plan to reflect your choice.`
Response shape is the same as `/api/app/changes`, always including the goal detail.

## 6. Existing endpoints the app also uses

Unchanged and still authoritative: `POST /api/auth/register|login|logout`, `GET /api/auth`,
`POST /api/coach` (chat — the only path that produces coaching interpretation),
`GET /api/proposals`, `POST /api/proposals/:id/approve|dismiss|preview`,
`POST /api/messages/:id/reaction`, `POST /api/learning` (`{id, version, action, requestId}` with
`action` in `agree|decline|pause|resume|close`), `GET/POST /api/provider`, `POST /api/provider/test`,
`GET /api/status`, `GET /api/connections`, `POST /api/connections/pair|unlink`,
`POST /api/tokens`, `POST /api/tokens/revoke`, `GET /api/calendars`, `POST /api/availability`,
`POST /api/bookings`, calendar connect/disconnect, `GET /api/events`.

For `POST /api/learning`, send `actionVersion` with `agree` and `decline`, and `version` with
`pause`, `resume` and `close`. The server rejects the other one.

## 7. Deep links

`sources[].deepLink` uses the `adler` scheme; register it in `Info.plist`.

| Record | Link |
| --- | --- |
| Learning record | `adler://insights/<recordId>` |
| Coach decision | `adler://insights?decision=<id>` |
| Saved context (memory) | `adler://insights?memory=<id>` |
| Message | `adler://coach/<conversationId>?message=<id>`, or `adler://coach?goal=<goalId>` |
| Goal | `adler://goals/<goalId>` |
| Action, result, milestone, checkpoint | `adler://goals/<goalId>?record=<id>` |
| Work block | `adler://calendar?goal=<goalId>` |
| Program version | `adler://settings/program` |

`deepLink` is `null` when the record no longer resolves.

## 8. Device testing on a LAN

With the dev server running (`npm run dev -- --port 8080`, which binds `0.0.0.0`), point the phone
at the Mac's private address, for example `http://192.168.1.24:8080`. The host allowance applies
only when `PUBLIC_URL` is unset and `NODE_ENV !== "production"`; a public hostname is still refused
with 403. Add `NSAllowsLocalNetworking` to the app's ATS settings for plain HTTP on the LAN. See
[docs/ios-app.md](ios-app.md).

## 9. Regenerating the examples

```sh
npx tsx scripts/app-api-examples.ts
```

It boots a runtime in a temporary directory, registers the fictional `casey-example` account, seeds
a labelled fictional workspace, exercises the real endpoints and writes `docs/ios-api-examples/`.
Dates are relative to the run date, so regenerate after changing any view.
