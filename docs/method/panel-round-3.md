Two rules in the same subsection give opposite answers to the same event, which is the defect §5.11.3 was rewritten to close.
   - Fix: Rewrite the definition: a crisis turn is any turn on which stage 1 fires under routes (b), (c) or (d), or on which stage 2 is answered yes, plus the remainder of that session. Add: a route (a) stage-1 fire closed by a stage-2 no makes only the fired turn and the stage-2 exchange non-extractable to `memories`; the session is not a crisis session, and nothing else changes (§5.11.3). 4. **§5.11.3 stage-2 rate limit, route (a) branch** — "At most once per 72 hours per user, except that any route (a) trigger is never rate-limited" — my round-two fix, implemented with no replacement bound of any kind. Route (a) triggers include hopelessness, entrapment and unbearable-pain statements, which recur within a single conversation. A user who writes "there's no way out of this" three times in one evening is handed the full-screen ASQ three times in one evening. A route (a) trigger in a new session is never rate-limited (see rewrite).

### New should fix

1. **§5.11.3 abandonment branch** — "If the user leaves without answering, the screen is re-presented once on next open; after a second abandonment it is replaced by a resource card and the check-in resumes; logged as an abandonment, not a no." Nothing else happens. A user who twice walked away from a direct suicide question resumes habit tapping with no safety flag, no post-crisis rule, no threshold change and no persistent resource. So a user who disclosed an eating disorder or drinking-to-cope yesterday is protected from one behavioural reply for 14 days and gets pre-mortems, friend questions and year questions the whole time.    - Fix: Once routes (c) and (d) set the safety flag (see must-fix on setting conditions), key both suppressions to the flag and delete the separate 14-day list in §5.4, so there is one window, one trigger set and one place to change it.
   - Basis: §9's own tag — every move is experimental, self-distancing g = 0.19 with a prediction interval spanning zero and one preregistered null with worse sleep — which is not a set of moves to run on a user who has just disclosed a risk marker; §5.11.10's stated intent; the method's single-definition principle applied everywhere else in v0.3.

   - Fix: Add to §11's Release gates and to §15.4 step 3: every number and link in the regional resource table dials and resolves, for every region in `users.crisis_region`'s domain, verified in the release candidate; any failure blocks release. Keep the quarterly re-verification in §15.4 step 5 as the between-release check.
   - Basis: Knysh & Pohrebniak 2026 (mean 24.9/65; "crisis resources buried behind chat and safety-critical links broken"); Pichowicz 2025 (0% adequate, mostly missing emergency contact information); safety-risk-detection.md §6 ("an eval you cannot re-run is a liability, not a gap" — and one that gates nothing is the same).
