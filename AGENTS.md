# Product and coaching changes

The user requires methodology-first engineering across Adler. Before changing product behavior, UX, onboarding, coaching, planning, progress, insights, adaptation or related claims, read `docs/product-principles.md`, `docs/method/adler-method.md` and the relevant sections of `docs/method/coaching-engineering.md`. The principles are the accepted product direction; the method describes the current runtime contract and limits; the engineering design specifies the target implementation. Never present target capabilities as already implemented. Use `CONTEXT.md` for domain terminology.

- Ground decisions in `docs/research/behavioural-science-synthesis.md` and its referenced deep dives. Keep evidence grades, transfer limits, source IDs and heuristic labels intact. The seven-method UI catalog alone is not the research base.
- Every substantive behavioural interpretation must trace to specific research claims and personal evidence. Distinguish theory, empirical findings, reported facts and tentative application; verify source support and applicability, not just valid citation IDs. The short UI explanation must reference the same saved rationale that informed the decision.
- Preserve one coaching system across web chat, intelligent app controls, SMS/iMessage, MCP and background reviews: shared methodology, model policy, tools, context, memory and authorization. Update the executable framework, prompts, schemas, evidence validation and relevant UI together when the behavior changes. Deterministic commands remain proportionate and use shared state/validation.
- Distinguish user-reported facts, hypotheses, controllable input, observed outcome and conditional projection. Never promote a sparse association into a confirmed personal rule or causal probability.
- Treat live hypotheses and tests as durable, goal-linked learning memory. Preserve original predictions, evidence versions, test states, review timing and corrections. Acceptance is not exposure, a review date is not a result, and cross-goal reuse needs a scoped transfer rationale.
- Choose cycles and action size for the user and goal type. Do not universalize historical habit thresholds or reproduce the old fixed intake script.
- Keep the user's next action and product value clear, with observation, specific behavioural rationale and expected effect available in simple language. Let users inspect scientific depth without requiring them to administer the methodology. Landing demonstrations and onboarding must establish useful understanding with low effort.
- Design the HOW deliberately: identify the inference, evidence, appropriate learning design, state changes, failure cases and observable verification before calling work complete. Use the simplest implementation that meets the scientific and product standard; extra prompts, citations or complexity alone do not meet it.
- Keep product changes surgical. Explain the framework connection and verify the affected behavior; do not add unrelated mechanics or invent research support.
- The user's current instructions and authorization take precedence over historical method/product documents. These instructions add no permission or approval gates.
